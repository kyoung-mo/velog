<h2 id="개요">개요</h2>
<p>2편에서는 STM32L4 주행 ECU와 MangoM32 화물함 ECU를 각각 단독으로 구현하고 검증하는 과정을 다뤘습니다.</p>
<p>이번 글에서는 그 이후에 진행된 실제로 시스템을 하나로 합치는 과정에서 겪은 일들을 정리했습니다. 각 보드 개별 구현에서 시간을 오래 쓰다보니, 통합하는 과정이 어려웠던 것 같습니다.</p>
<hr />
<h2 id="1-통합-시작--개별은-됐는데-붙이니까-달랐다">1. 통합 시작 — 개별은 됐는데 붙이니까 달랐다</h2>
<p>프로젝트 기간은 2주였습니다. 처음 계획은 1주 안에 하드웨어를 완성하고, 나머지 1주를 통합과 테스트에 쓰려고 생각했으나, 현실은 달랐습니다.</p>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/0471f805-10f2-47f8-8b9e-fd3e94e9a507/image.png" /></p>
<p>CAN 통신 트러블슈팅, 트랜시버 문제, 핀 충돌 이슈 등등을 해결하다 보니 <strong>하드웨어가 완성된 시점이 마감 3~4일 전</strong>이었습니다. 통합에 쓸 수 있는 시간이 굉장히 촉박하여, 다들 아침 9시부터 저녁 10시는 기본으로 남아서 진행했습니다.</p>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/39b3098a-7663-4e20-9912-0935beee79e7/image.png" /></p>
<p>개발은 역할을 나눠 병렬로 진행했습니다.</p>
<ul>
<li><strong>RPi1 + STM32L4</strong> → 주행 테스트 (2명)</li>
<li><strong>RPi3</strong> → MQTT 서버 구축 (1명)</li>
<li><strong>RPi4 + MangoM32</strong> → 클라이언트 UI + STMF103 보드의 구현 안될 것 대비하여 다른 보드로 화물함 ECU 동작 구현 (1명)</li>
<li><strong>저는</strong> STM32L4 주행 ECU 배선과 CAN 통신 완성 → MangoM32(STMF103) 화물함 ECU CAN 검증을 이어서 진행했습니다.</li>
</ul>
<p>각자 맡은 파트가 개별적으로 동작하기 시작하면서, 이제 하나로 합칠 차례였습니다.</p>
<hr />
<h2 id="2-rpi1-벽돌--프로젝트-위기">2. RPi1 벽돌 — 프로젝트 위기</h2>
<p>마감 4일 전이었습니다.</p>
<p>주행 ECU와 미션 ECU를 담당하던 팀원들이 VNC 설정을 해보겠다며 패키지를 설치하고 재부팅을 반복했습니다. 그 과정에서 <strong>RPi1이 부팅되지 않는 상태</strong>가 되었습니다.</p>
<p>시스템의 핵심 노드가 사실상 멈춘 상황이었습니다.</p>
<p>이 상태를 그냥 두면 일정 자체가 밀릴 수 있다고 판단했습니다. 마감이 얼마 남지 않은 시점이라, 원인을 깊게 추적하기보다 시스템을 최대한 빨리 복구하는 쪽이 더 중요하다고 판단했습니다.</p>
<blockquote>
<p><strong>즉시 라즈베리파이 초기화를 결정했습니다.</strong></p>
</blockquote>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/df840829-d96b-4b17-aff7-28f19e1a7f72/image.png" /></p>
<p>그런데 초기화 과정에서도 문제가 생겼습니다. 기존 SD카드에서 OS 설치 오류가 반복됐습니다. SD카드 자체가 손상되었다고 생각했습니다.</p>
<p>결국 새 SD카드로 교체하고, 처음부터 환경을 다시 구성했습니다.</p>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/9bc07910-1397-47a2-88ef-d543c1950f62/image.png" /></p>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/a02a5cda-3035-4490-9c19-da54f6381e4d/image.png" /></p>
<p>다행이 이전에 사용하던 코드는 Notion과 GitHub에 올라가 있었습니다. 초반에 하루하루 한 일을 다른 팀원도 확인할 수 있도록 매일 각자 한 일을 적는 페이지를 만들어두었고, 보드 별 최신 코드 정리라는 페이지도 만들어, 목표한 동작에 최대한 가깝게 문제없이 동작하는 코드를 업데이트 해두자고 말해둔 것이 다행이였습니다. </p>
<p>깃허브는 저도, 팀원도 다들 익숙치 않은 상황이라 노션을 메인으로 하되, 최신 코드는 깃허브에도 clone 하는 연습을 진행하자고 회의 때 계속 언급했었습니다. </p>
<p>덕분에 환경 복구는 빠르게 진행할 수 있었다고 생각하고, 주행 ECU와의 연결도 다시 잡았습니다.</p>
<p>이후 주행 ECU + 미션 ECU는 팀원들에게 다시 넘기고, 저는 MangoM32 화물함 ECU 하드웨어를 완성하는 작업으로 넘어갔습니다.</p>
<blockquote>
<p>이 경험 이후로 백업, GitHub 커밋의 중요성에 대해 알게 됐습니다. 코드가 올라가 있지 않았다면 복구하는 데 얼마나 시간이 더 걸렸을지 예상이 잘 안됩니다.</p>
</blockquote>

<h2 id="3-3노드-통합--드디어-하나로">3. 3노드 통합 — 드디어 하나로</h2>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/e914c07f-6469-4cc3-8151-803b66affd21/image.png" /></p>
<p>MangoM32 화물함 ECU 하드웨어가 완성되고 나서, 세 노드를 하드웨어에 하나에 연결했습니다.</p>
<pre><code>STM32L4 (주행 ECU) ── CAN 버스 ── RPi1 (미션 ECU) ── CAN 버스 ── MangoM32 (화물함 ECU)</code></pre><p>CAN 버스에 3개 노드가 동시에 올라간 상태에서 처음으로 전체 주행 흐름을 돌렸습니다. RPi1이 라인을 따라가며 CAN 0x010으로 주행 명령을 보내고, STM32가 PID로 모터를 제어하고, ArUco 마커를 감지하면 MangoM32에 도착 신호(0x013)를 전달하는 흐름이었습니다.</p>
<p>개별로 테스트했을 때와 달리, 전체 흐름에서는 타이밍이 중요했습니다.</p>
<pre><code>ArUco 도착 인식 → CAN 0x013 전송 → MangoM32 인증 대기 → 도어 닫힘(0x301) 수신 → 유턴</code></pre><p>이 순서가 조금만 어긋나도 차량이 도착 후 멈춘 채 다음 상태로 넘어가지 않거나, 유턴이 너무 빨리 시작되는 문제가 발생했습니다. 각 노드의 상태 전환 순서를 맞추는 데 시간이 걸렸습니다.</p>
<p>이 과정에서 저는 CAN 메시지 흐름과 상태 전환 순서를 정리하며, 각 ECU 간 동작 타이밍을 맞추는 역할을 담당했습니다.</p>
<hr />
<h2 id="4-전체-시스템--연결할수록-복잡해졌다">4. 전체 시스템 — 연결할수록 복잡해졌다</h2>
<p>3노드 통합 이후, RPi3(MQTT 서버)와 RPi4(클라이언트)까지 포함한 전체 시스템을 구성했습니다.</p>
<pre><code>RPi4 → RPi3 → RPi1 → STM32 / MangoM32
(주문) (서버) (미션 ECU) (CAN 노드들)</code></pre><p>각 단계에서 작은 불일치들이 계속 나왔습니다.</p>
<p>예를 들어 서버는 <code>delivery/vehicle/{id}/order</code>로 출동 명령을 발행하고 있었는데, RPi1 쪽에서는 다른 이름의 토픽을 구독하고 있어 출동 명령이 아예 도달하지 않는 경우가 있었습니다. 토픽 이름 하나 차이로 명령이 전달되지 않는 것이라 원인을 찾기까지 시간이 걸렸습니다. 메시지 타이밍이 맞지 않아 명령이 처리되지 않거나, CAN 명령 전달 순서가 어긋나 상태머신이 예상과 다르게 동작하는 문제도 있었습니다.</p>
<p>개별적으로 보면 사소한 문제들이었습니다. 하지만 전체 시스템에서는 연쇄적으로 영향을 주면서 동작이 계속 깨졌습니다.</p>
<blockquote>
<p><strong>각 파트를 담당할 때는 보이지 않던 문제들이, 연결하는 순간 한꺼번에 드러났습니다.</strong></p>
</blockquote>
<hr />
<h2 id="5-교차로에서-멈추지-않는-문제">5. 교차로에서 멈추지 않는 문제</h2>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/1fc196e6-38c3-4b38-a9d9-60dd5a4e5af9/image.gif" /></p>
<p>3노드를 연결하고 주행 테스트를 시작하자마자 이상한 현상이 나타났습니다.</p>
<p>교차로에서 정지 명령을 보내는데 차가 멈추지 않았습니다. 방향 명령도 간헐적으로 무시됐습니다. RPi1 로그를 확인해보면 명령은 분명히 송신되고 있었습니다.</p>
<p>&quot;명령은 나가는데 STM32가 못 받는 건가?&quot;</p>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/5279d92d-540c-46be-8f8a-539474996bfb/image.png" /></p>
<p>원인을 추적해보니 두 가지 문제가 겹쳐 있었습니다.</p>
<p><strong>원인 1 — O_NONBLOCK으로 인한 명령 드롭</strong></p>
<p>CAN 수신 쪽을 한참 들여다봤지만 문제가 없었습니다. 결국 송신 코드를 다시 보다가 원인을 찾았습니다.</p>
<p>처음에는 블로킹으로 인한 지연을 줄이기 위해 non-blocking으로 설정했었습니다. 그런데 <code>send_cmd()</code> 함수 내부에서 매 호출마다 <code>fcntl(O_NONBLOCK)</code>을 설정하고 있었고, SocketCAN TX 버퍼가 가득 찬 순간, STOP이나 LEFT 같은 명령이 <code>EAGAIN</code> 에러를 내면서 <strong>조용히 드롭</strong>되고 있었던 것입니다.</p>
<p>에러 메시지도 없었고, 로그상으로는 정상이었습니다. 문제는 CAN 자체가 아니라, 보내는 쪽 소켓 설정이었습니다.</p>
<p>해결은 간단했습니다. <code>send_cmd()</code> 내부의 <code>fcntl(O_NONBLOCK)</code> 두 줄을 제거하고 blocking write로 변경했습니다. 이후 명령 드롭이 사라졌습니다.</p>
<p><strong>원인 2 — IWDG 딜레이로 인한 응답 지연</strong></p>
<p>명령 드롭 문제를 해결했는데도 교차로에서 직진을 조금 더 하다가 멈추는 현상이 남아 있었습니다.</p>
<p>설계 단계에서 IWDG(Independent Watchdog)를 300ms 타임아웃으로 설정해두었는데, 카메라 기반 라인트레이싱 특성상 OpenCV 연산 시간이 일정하지 않아 프레임마다 처리 딜레이가 생겼습니다. 이 딜레이가 IWDG Refresh 타이밍에 영향을 주면서 명령 응답이 늦어지는 것이 원인이었습니다.</p>
<pre><code class="language-c">// 10ms 마다 TIM6 인터럽트
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim-&gt;Instance == TIM6) {
        pid_flag = 1;
        if (can_timeout_cnt &lt; 0xFFFF) can_timeout_cnt++;
    }
}

// CAN 수신 시 카운터 리셋
can_timeout_cnt = 0;

// CAN 타임아웃 (5000ms 동안 0x010 미수신 시 Motor_Stop() 호출)
if (can_timeout_cnt &gt;= (CAN_CMD_TIMEOUT_MS / PID_INTERVAL_MS)) {
    if (current_dir != DIR_STOP) {
        Motor_Stop();
        UART_Print(&quot;[TIMEOUT] STOP\r\n&quot;);
    }
}</code></pre>
<p>결국 IWDG를 제거하고, 소프트웨어 타임아웃 방식으로 대체했습니다. 5초 동안 CAN 명령이 수신되지 않으면 <code>Motor_Stop()</code>을 직접 호출하는 방식입니다. RPi1 처리 딜레이로 인한 문제는 전이랑 비교했을 때 훨씬 잘 동작했습니다.</p>
<blockquote>
<p><strong>IWDG</strong>는 MCU hang 상황에 대비한 하드웨어 안전장치로 설계했지만, 카메라 처리 딜레이와 맞물려 오히려 불안정 요소가 됐습니다. 추후 <strong>프로젝트 디벨롭 과정</strong>에서 카메라 없이 초음파 센서 기반으로 재설계할 때 다시 적용해볼 예정입니다.</p>
</blockquote>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/4a656f58-32ee-484e-9399-5b487d1cff21/image.gif" /></p>
<blockquote>
<p>이번 문제는 에러가 보이지 않았기에 찾는데 어려움이 었습니다. 코드도 정상, 로그도 정상인데 동작만 이상한 상황이였기 때문입니다.</p>
</blockquote>

<h2 id="6-환경의-문제점-ㅡ-모터-전류-부족과-바닥-재질">6. 환경의 문제점 ㅡ 모터 전류 부족과 바닥 재질</h2>
<p>통신 문제를 해결하고 나서 주행 테스트를 이어가는데, 라인트레이싱에서 회전을 진행한 후 라인 재정렬 과정이 불안정했습니다.</p>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/ec3e4d63-cc5d-49c7-8237-4ff5cdc549a6/image.png" /></p>
<p>처음에는 카메라 설정이나 임계값 문제라고 생각했습니다. 파라미터를 계속 조정해봐도 근본적으로 해결이 되지 않았습니다.</p>
<p>테스트를 반복하면서 다른 가능성을 떠올렸습니다.</p>
<p><strong>&quot;혹시 모터 출력에 필요한 전류가 부족한 게 아닐까?&quot;</strong></p>
<p>사용한 모터는 최대 330RPM 사양이었습니다. 그리고 L298N 드라이버 하나로 4개의 모터를 A상/B상 각 2개씩 병렬로 구동하는 구조였습니다. 이 구조에서는 각 모터에 공급되는 전류가 나뉘어 들어가기 때문에, 토크가 충분히 나오지 않을 수 있다고 생각했습니다.</p>
<p>여기에 트랙 바닥 재질 문제까지 겹쳤습니다. 처음 사용한 보드롱 재질은 표면이 미끄러워 바퀴가 헛돌았습니다. 토크가 약한 상황에서 바닥 마찰력까지 낮으니 제어가 불안정해질 수밖에 없었습니다.</p>
<p><img alt="" src="https://velog.velcdn.com/images/mommers/post/5a2bbc44-1500-46e5-aea6-6bbe282e1f25/image.png" /></p>
<p>결국 주행 환경은 A4 용지로 교체하였고, 전류 부족을 예상하여 모터 드라이버 하나 더 추가하는 과정은 하드웨어를 전부 뜯어 고치기에는 부족한 시간이라서 넘어갔습니다. 이후 주행이 그나마 안정됐습니다. </p>
<blockquote>
<p>설계 단계에서 모터 드라이버 구조를 더 꼼꼼하게 검토했어야 했다는 아쉬움이 남습니다. 
모터에 따른 하드웨어가 추가됨에 따라 하드웨어의 무게가 점점 늘면서, 초반에 테스트했던 환경과 많이 달랐던 문제도 있었습니다.</p>
</blockquote>
<hr />
<h2 id="7-통합에서-드러난-커뮤니케이션-문제">7. 통합에서 드러난 커뮤니케이션 문제</h2>
<p>기술적인 문제보다 더 뒤늦게 발견된 문제가 하나 있었습니다.</p>
<p>발표 하루 전 저녁, 클라이언트 UI 동작을 확인하다가 주문 완료 이후 화면이 넘어가지 않는 걸 발견했습니다.</p>
<p>원래 계획은 아래와 같습니다.</p>
<pre><code>주문 완료 → 배달 중 화면 (진행률 표시) → 배달 완료 알림 → 초기 주문 화면</code></pre><p><img alt="" src="https://velog.velcdn.com/images/mommers/post/858d39d3-5127-42af-8fa2-66736da87cbe/image.png" /></p>
<p>그런데 모든 과정이 완료되어갈때쯤 확인해보니 주문 완료까지만 구현되어 있었습니다.</p>
<p>이유를 물어보니, 하드웨어가 목적지까지 실제로 동작해야 그 이후 흐름을 구현할 수 있었는데, 주행 테스트가 늦어지면서 그 부분을 진행하지 못했다는 답변이 돌아왔습니다.</p>
<p>그 자체는 충분히 이해할 수 있는 상황이었습니다. 하지만 그렇게 결정을 했으면 미리 알려줬으면 좋았을 것 같다고 생각했습니다. 프로젝트 2주의 기간 중 첫 1주는 회의 과정을 거치며 서로 어디까지 진행됐는지 파악하는 시간을 가졌으나, 마감 기한이 다가올수록 다들 구현이 시급해져서 회의 시간을 적게 가지게 된 것도 문제라고 생각합니다.</p>
<p>저는 주행 테스트가 이어지는 동안 서버와 클라이언트 담당자가 그쪽 작업을 병렬로 진행하고 있다고 생각했습니다. 중간중간 &quot;잘 동작하지?&quot; 물어볼 때 &quot;문제없다&quot;는 답변이 왔고, 그걸 그대로 믿었습니다. 구체적으로 어디까지 구현됐는지는 확인하지 않았습니다.</p>
<p>결국 미완성인 상태로 발표를 진행했으나 프로젝트에서 핵심이라고 생각한 주문-&gt;서버-&gt;Rpi1 MQTT 통신 방식, 차량 내 CAN 통신을 통한 주행은 발표 내용에서 얘기할 수 있었어서 그나마 다행이라고 생각했습니다.</p>
<p>각자 파트를 병렬로 진행할 때는 하루 30분이라도 잡아서 회의를 거치며 각자 어디까지 진행됐고, 다음은 어떤걸 진행할 예정인지 얘기해보는 시간을 가지는 것과, <strong>&quot;잘 되고 있어?&quot;</strong> 한 마디보다 <strong>&quot;어디까지 됐어?&quot;</strong> 라고 물어야겠다고 생각했습니다. </p>
<p>진행 상태를 구체적으로 공유하는 기준이 없으면, 이번 경험처럼 발표 전날에야 문제를 알게 되는 상황이 생길수도 있기 때문입니다. 다음 프로젝트에서는 아무리 구현이 시급해도 회의하는 시간을 짧게나마 가지는 시간을 가져볼 생각입니다.</p>
<hr />
<h2 id="마치며">마치며</h2>
<p>이 프로젝트를 통해 가장 크게 느낀 건 두 가지입니다.</p>
<p>첫째, <strong>개별 기능이 정상이라고 해서 시스템이 정상 동작하는 것은 아니라는 점</strong>입니다. CAN 통신도 되고, MQTT도 되고, 모터도 돌아가는데, 합친다고 바로 안되는 것을 확인했습니다. 통합은 그 자체로 별도의 작업임을 깨달았습니다. </p>
<p>하지만 통합 직전 개별 테스트는 반드시 필요한 과정입니다. 만약 처음부터 전부 합치고 시작했다면 큰 구조 중 어느 부분이 문제인지 파악하기 힘들었을 것입니다.</p>
<p>둘째, <strong>평소 습관이 위기 상황에서 차이를 만든다는 점</strong>입니다. RPi1이 벽돌이 됐을 때, Notion과 GitHub에 코드가 올라가 있지 않았다면 복구가 훨씬 오래 걸렸을 것입니다.</p>
<p>시스템은 코드가 아니라, 연결과 타이밍 위에서 동작한다는 것을 이번 프로젝트에서 처음으로 체감했습니다. 통합은 구현의 마지막 단계가 아니라, 개별 기능을 다시 검증하게 만드는 또 하나의 개발 단계였습니다.</p>
